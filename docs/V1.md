# Handpicked: v1 Spec

## Goal

A weekly job that generates a few good, per-user suggestions for titles not yet in the library, queues them as pending requests in Seerr on behalf of each household member, and sends the admin a digest explaining who each pick is for and why.

v1 should be immediately useful to the admin and should test whether the curator model feels right before building delivery and measurement.

## Scope

**In:**

- Ingest per-user watch history from Tautulli
- Generate candidates from TMDB recommendations
- Filter, score, and pick the top N per user
- Create pending Seerr requests attributed to each user
- Send a weekly digest to the admin
- Record every suggestion in a lifecycle table

**Out (deliberately):**

- Per-user Plex labels or home-screen rows (v2)
- Hit-rate and outcome reporting (v2)
- LLM-generated explanations (optional, later)
- Group recommendations (parked)
- Any web UI beyond, at most, a simple status page
- Custom approval UI (Seerr's queue is the gate)

## Inputs

| Source | Used for |
|---|---|
| Tautulli | Per-user watch history, including completion percentage and rewatches |
| TMDB | Recommendations and similar titles per seed; title details; Canadian certifications; vote count and rating |
| Seerr | What is already owned (Seerr syncs both Plex and Radarr/Sonarr); existing, pending, and declined requests; blocklist; household users |

## Pipeline (weekly, per user)

1. **Seeds:** titles the user finished (default: 80% or more complete) in the last 90 days.
   - Weight by recency.
   - Boost rewatches.
   - Titles abandoned under 25% complete count as a mild negative signal.
   - TV is judged per show, since history is per episode. A show is a seed if the user finished at least 3 episodes in the window, weighted by the most recent finished episode. It counts as abandoned if the user watched only 1 or 2 episodes and has not returned in some weeks. Rewatched episodes boost the show.
2. **Candidates:** union of TMDB recommendations across all of the user's seeds.
3. **Filter:** drop any candidate that is:
   - already owned
   - already requested, pending, or declined in Seerr
   - on the Seerr blocklist
   - previously suggested to this user (any lifecycle state)
   - already in the user's own watch history (for titles watched, then removed from the library)
   - rated above the user's max age (see open question 3)
   - below a minimum TMDB vote count
4. **Score:** keep it simple and explainable:
   - sum over seeds that recommend the candidate of (seed weight)
   - plus a small quality prior from TMDB rating
   - minus a penalty if the candidate is similar to abandoned titles
5. **Select:** top N per user (default 3 to 5). A title picked for one user is not picked for another in the same run, since Seerr takes one request per title. Picks for a user with no Seerr link do not count, since they cannot be requested.

Users with fewer than a minimum number of seeds are skipped in v1 rather than guessed at.

## Outputs

1. **Pending Seerr requests, created on behalf of each user,** so the approval queue reads "requested by <user>." Household members are imported as Seerr users; they never need to log in. Requests stay pending until the admin approves. TV requests use `seasons: "all"` (Seerr skips specials and empty seasons); the admin can trim seasons on the pending request before approving.
2. **Weekly digest to the admin** (email to start), grouped by user. For each pick: title, year, certification, and the seeds that produced it ("because you finished X and Y"). This is the context Seerr's queue does not show.

## Core data model

The `suggestions` table is the heart of the product. Every suggestion gets a row from day one, even though v1 only fills in the early states.

**Lifecycle:**

```
proposed -> requested -> approved | declined -> available -> watched | abandoned | ignored
```

**Fields (initial):**

- id
- user (Plex/Seerr user)
- tmdb_id, media_type (movie / tv)
- score
- seeds (list of TMDB ids and their weights)
- status
- seerr_request_id
- timestamps per status transition

Supporting tables: `users` (discovered household members, their Seerr link, and per-user settings: include, max age, picks per run), `watch_events` (ingested from Tautulli), and a TMDB cache.

v2's delivery and measurement features should mostly be updates to `suggestions` rows, not new structures.

## Configuration

- Service URLs and API keys: Tautulli, TMDB, Seerr
- Schedule as a cron expression (default: weekly)
- Default picks per run (per-user settings live in the `users` table, see "Users live in SQLite" below)
- Thresholds: completion %, abandon %, seed window, minimum seeds, minimum TMDB vote count, minimum finished episodes for a TV seed, weeks before a TV show counts as abandoned
- Digest delivery settings (SMTP to start)
- Dry-run mode: compute and report everything, write nothing to Seerr. On by default, so a fresh install writes nothing until the admin turns it off

## Technical decisions

- **Language:** Python (3.14, managed with uv). The main reason is v2: delivery relies on Plex share label filters, which `python-plexapi` already supports. It also fits the self-hosted *arr ecosystem. No web framework in v1.
- **Storage:** SQLite at `/config/handpicked.db`, WAL mode, accessed with stdlib `sqlite3` and hand-written SQL. No ORM.
- **Migrations:** numbered `.sql` files tracked with `PRAGMA user_version`, applied automatically at startup so updating the image needs no manual step.
- **Config:** YAML at `/config/config.yml`, validated with pydantic. Env vars can override secrets (API keys, SMTP password) so they can live in the Unraid template instead of the file.
- **Users live in SQLite and are opt-in:** discovery records every active Tautulli user in `users` (skipping Tautulli's `Local` placeholder), linked to a Seerr user (see open question 1), with `include` off. Only included users get picks. Including a user is when the admin sets their max age; without the opt-in, a forgotten kid account would get unrestricted picks. The digest lists discovered users who are not included.
  - Settings change through the CLI, e.g. `docker exec handpicked handpicked users set kid --include --max-age 10`. `handpicked users` lists users with their Seerr link and settings.
  - Users live only in the database rather than in `config.yml`, so they are never split across two places and nothing has to be typed in by hand to match. A web UI to manage them is a likely later addition over the same table.
- **Runtime:** a long-running container with an internal scheduler (APScheduler 3.x, cron trigger), since Unraid expects containers to stay up and v2 will likely add more jobs. Manual runs via CLI, e.g. `docker exec handpicked handpicked run --dry-run`.

## Open questions (verify before writing much code)

1. **Seerr on-behalf-of requests (resolved, verified against Seerr v3.5.1 source and a live run):** yes, in two calls. Seerr decides approval from the caller's permissions and attribution from the `userId` field. Setting `userId` on a new request needs both `MANAGE_USERS` and `MANAGE_REQUESTS`, and `MANAGE_REQUESTS` approves the request, so no single call creates a pending request for someone else. Instead:
   - Handpicked creates the request as a dedicated local Seerr user (e.g. "Handpicked"), using the admin API key with an `X-API-User: <its seerr user id>` header and no `userId`. The request is pending, attributed to that user.
   - It then reassigns the request to the household member with `PUT /api/v1/request/:id` and `userId`, as the admin. Only pending requests can be edited, and editing keeps them pending. Members keep any auto-approve permission for their own direct and watchlist requests.
   - If the reassign fails, Handpicked deletes the request, so the queue never shows a pick as requested by Handpicked.
   - The Handpicked user's Seerr id is set in config as `services.seerr.request_user_id`. It needs `REQUEST` and must not have `ADMIN`, `MANAGE_REQUESTS`, or any auto-approve permission, since any of those approve the request. Check its permissions before creating requests. Its own quota applies when creating, so it should have no request limit.
   - Seerr's "new request" notification names the Handpicked user, since the notification is sent before the reassign.
   - The member's quota is checked on the reassign. The member does not need the `REQUEST` permission. Handle quota errors per pick and report them in the digest. A refused pick gets no `suggestions` row, so it can be picked again in a later run.
   - `X-API-User` and `userId` take Seerr's internal user ids, not Plex ids. `users` stores each member's Seerr id (Seerr exposes `plexId` for the mapping; it equals Tautulli's `user_id`).
   - Seerr's Plex import skips accounts with no email, which includes Plex Home managed users (typically kids, including "Teen" profiles). For those, the admin creates a local Seerr user (username and password, no real email needed; the default `REQUEST` permission is enough). Imported users match on `plexId` automatically. Local users have no `plexId`, so discovery links them by name: Tautulli records a managed user's profile name as its username, and a local Seerr user with the same username (ignoring case) is linked. The link is then kept by Seerr id, so renaming either side does not break it. Only Seerr users without a `plexId` are considered, so an adult's account is never matched to a kid's profile. Missing or ambiguous matches are reported, and the admin can link explicitly with `handpicked users link`, which discovery never overwrites.
   - Members may get Seerr's approved and available notifications for these requests. Leaving notification settings alone for now to see how it lands.
2. **Tautulli history fields (resolved, verified against Tautulli v2.18.2 source):** use `get_history` with `grouping=0` (raw sessions), paged with `start`/`length`. Each row has `reference_id`, `user_id` (the Plex account id, which matches Seerr's `plexId`), `percent_complete`, `watched_status`, `started`/`stopped`, `media_type`, `rating_key`, and `grandparent_rating_key` (the show, for episodes).
   - Use `percent_complete` against our own thresholds rather than `watched_status`, which depends on the admin's Tautulli settings.
   - Tautulli decides when a session continues an unfinished viewing at write time and records it in `reference_id`, which never changes afterwards. Grouped rows (`grouping=1`) do change when a viewing is resumed later, so ingest raw sessions (append-only, simple incremental sync) and group by `reference_id` ourselves. `percent_complete` is the playback position, so the max over a viewing's sessions is its completion. A second complete play is a new viewing, so a rewatch is two or more finished viewings of the same item.
   - Always pass `grouping` explicitly; omitted, it follows the admin's Tautulli setting.
   - Ingest full history incrementally into `watch_events` (every user, not just included ones), not just the seed window, so older first watches are visible.
   - History has no TMDB id, only Plex's own `guid`. Resolve it with `get_metadata` on the `rating_key` (or `grandparent_rating_key` for TV), which returns `guids` including `tmdb://`, and cache the result. This only works while the item is still in Plex; skip unresolvable items and log the count. Not worth a fallback unless the count turns out to matter.
3. **TMDB certifications (resolved, from TMDB API docs):** fetch with the title details via `append_to_response`. Movies: `release_dates`, entry for `CA`, prefer the theatrical (type 3) certification, else the first non-empty one. TV: `content_ratings`, entry for `CA`.
   - Canada rates movies (`E, G, PG, 14A, 18A, R, A`) and TV (`Exempt, C, C8, G, PG, 14+, 18+`) on different scales, so the per-user setting is a max age, with small mapping tables from each rating to an age (e.g. movie `14A` is 14, TV `C8` is 8).
   - No Canadian rating: fall back to the US rating, mapped to an age the same way.
   - No rating at all: fail closed. Exclude for users with a max age, allow for unrestricted users.
   - Quebec (`CA-QC`) ratings are ignored.
4. **Owned-check source (resolved, verified against Seerr v3.5.1 source):** neither; use Seerr. Its Plex scans mark library titles available (including ones added outside the *arr stack), and its Radarr/Sonarr scans import every movie and series there, marking monitored-but-missing titles as processing. Page through `GET /api/v1/media` once per run; a title is owned if `status` or `status4k` is processing, partially available, or available.
   - Depends on Seerr's Plex and *arr scan jobs being enabled (the default). Data is at most a day stale, which is fine for a weekly job.
   - Still use the request list for declines, since a decline resets media status (see question 5).
   - Radarr and Sonarr are dropped from v1 and kept as possible future integrations if a need comes up.
5. **Declined requests in Seerr (resolved, verified against Seerr v3.5.1 source):** declining keeps the request row with status `DECLINED`, but resets the media status to unknown, so the title becomes requestable again and only the request rows remember the decline. `GET /api/v1/request?filter=all` includes declined requests (there is no `declined` filter, so page and filter client-side); it excludes blocklisted media, which come from `GET /api/v1/blocklist` instead.
   - Not every decline is the admin's: Seerr's Radarr/Sonarr scan auto-declines approved requests whose title is no longer on any server. Treat all declines as "do not suggest" anyway.
   - Seerr requests can be hard-deleted (manual delete, user deletion). The `suggestions` table is the source of truth for never re-suggesting: each run checks open requests by `seerr_request_id` and records `declined` locally. The Seerr-wide request list and blocklist are extra filters for titles requested or blocked outside Handpicked.
