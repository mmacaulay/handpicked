# Handpicked: v1 Spec

## Goal

A weekly job that generates a few good, per-user suggestions for titles not yet in the library, queues them as pending requests in Seerr on behalf of each household member, and sends the admin a digest explaining who each pick is for and why.

v1 should be immediately useful to the admin and should test whether the curator model feels right before building delivery and measurement.

## Scope

**In:**

- Ingest per-user watch history from Tautulli
- Generate candidates from TMDB recommendations
- Filter, score, and pick the top N per user
- Create pending Seerr requests attributed to each user
- Send a weekly digest to the admin
- Record every suggestion in a lifecycle table

**Out (deliberately):**

- Per-user Plex labels or home-screen rows (v2)
- Hit-rate and outcome reporting (v2)
- LLM-generated explanations (optional, later)
- Group recommendations (parked)
- Any web UI beyond, at most, a simple status page
- Custom approval UI (Seerr's queue is the gate)

## Inputs

| Source | Used for |
|---|---|
| Tautulli | Per-user watch history, including completion percentage and rewatches |
| TMDB | Recommendations and similar titles per seed; title details; Canadian certifications; vote count and rating |
| Radarr / Sonarr (or Plex) | What is already owned |
| Seerr | Existing, pending, and declined requests; household users |

## Pipeline (weekly, per user)

1. **Seeds:** titles the user finished (default: 80% or more complete) in the last 90 days.
   - Weight by recency.
   - Boost rewatches.
   - Titles abandoned under 25% complete count as a mild negative signal.
2. **Candidates:** union of TMDB recommendations across all of the user's seeds.
3. **Filter:** drop any candidate that is:
   - already owned
   - already requested, pending, or declined in Seerr
   - previously suggested to this user (any lifecycle state)
   - above the user's maximum certification
   - below a minimum TMDB vote count
4. **Score:** keep it simple and explainable:
   - sum over seeds that recommend the candidate of (seed weight)
   - plus a small quality prior from TMDB rating
   - minus a penalty if the candidate is similar to abandoned titles
5. **Select:** top N per user (default 3 to 5).

Users with fewer than a minimum number of seeds are skipped in v1 rather than guessed at.

## Outputs

1. **Pending Seerr requests, created on behalf of each user,** so the approval queue reads "requested by <user>." Household members are imported as Seerr users; they never need to log in. Requests stay pending until the admin approves.
2. **Weekly digest to the admin** (email to start), grouped by user. For each pick: title, year, certification, and the seeds that produced it ("because you finished X and Y"). This is the context Seerr's queue does not show.

## Core data model

The `suggestions` table is the heart of the product. Every suggestion gets a row from day one, even though v1 only fills in the early states.

**Lifecycle:**

```
proposed -> requested -> approved | declined -> available -> watched | abandoned | ignored
```

**Fields (initial):**

- id
- user (Plex/Seerr user)
- tmdb_id, media_type (movie / tv)
- score
- seeds (list of TMDB ids and their weights)
- status
- seerr_request_id
- timestamps per status transition

Supporting tables: `users` (with per-user settings like max certification), `watch_events` (ingested from Tautulli), and a TMDB cache.

v2's delivery and measurement features should mostly be updates to `suggestions` rows, not new structures.

## Configuration

- Service URLs and API keys: Tautulli, TMDB, Radarr, Sonarr, Seerr
- Schedule (default: weekly)
- Per-user settings: include/exclude, max certification, picks per run
- Thresholds: completion %, abandon %, seed window, minimum seeds, minimum TMDB vote count
- Digest delivery settings (SMTP to start)
- Dry-run mode: compute and report everything, write nothing to Seerr

## Open questions (verify before writing much code)

1. **Seerr on-behalf-of requests:** can an admin API key create a request attributed to another user? The design leans on this. If not, fall back to requests from a service account with the intended user recorded in the digest and the `suggestions` table.
2. **Tautulli history fields:** confirm the fields for completion percentage, watched status, and user, and how rewatches appear.
3. **TMDB certifications:** confirm how Canadian movie certifications and TV content ratings are exposed, and what to do when a title has no Canadian rating.
4. **Owned-check source:** Radarr/Sonarr vs. Plex library. Radarr/Sonarr also catch titles that are monitored but not yet downloaded.
5. **Declined requests in Seerr:** confirm how declined requests are retained and queried, so they are never re-suggested.

## Done when

- [ ] Dry run produces sensible top picks for each household user
- [ ] Pending requests appear in Seerr attributed to the right users
- [ ] Weekly digest arrives with per-user picks and their seeds
- [ ] Re-running the job does not duplicate suggestions or re-suggest declined titles
- [ ] Every suggestion is recorded in `suggestions` with correct status
- [ ] Runs as a Docker container on Unraid on a schedule
